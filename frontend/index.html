How it works

One CIBIL PDF in, the Full Detail Excel workbook out — with a Maker–Checker gate in between. The pipeline first recognises whether the upload is an individual or a commercial CIBIL report and adapts its extraction accordingly, then processes it with Azure Document Intelligence and the Microsoft Foundry model gpt-5.4-mini (the same instructions registered as the cibil-extractor agent), and finishes with a rule engine and Excel generator. The step-by-step below traces one report end to end.

What runs on every report: the PDF's embedded text is read with pypdfium2, the report type (individual vs commercial) is recognised, and the accounts are extracted from the clean text layer; Azure Document Intelligence OCR runs only when a PDF has no text layer (a scan). The report text plus the extraction instructions go to the Foundry gpt-5.4-mini deployment, which returns structured JSON; a rule engine then normalises, summarises and reconciles it; on approval, Excel is generated. Keyless throughout (managed identity + RBAC).

Step by step — from upload to Excel

StepWhat it doesWhy
1. Upload
Browser → FastAPI		 The maker drops a CIBIL PDF in the browser; it is sent to POST /api/extract as multipart. One entry point; the file is streamed and parsed in memory, never written to disk.
2. Read text & recognise report type
pypdfium2		 FastAPI extracts the PDF's embedded text, one line per row, then recognises whether it is an individual / consumer or a commercial CIBIL report and picks the matching extraction strategy. Born-digital CIBIL PDFs carry an exact text layer, so reading it directly avoids OCR errors (pypdfium2 is permissively licensed, BFSI-safe); the report type decides how the text is chunked for the model.
3. OCR & layout
Azure Document Intelligence · scans only		 DI (prebuilt-layout) runs only when a PDF has no text layer (a scan / photo). Every born-digital report — individual or commercial — skips it and uses the clean text layer. Makes scanned reports work while removing the slowest step for born-digital PDFs, where the pypdfium2 text is authoritative (DI's OCR mis-reads the ₹ glyph). Skipping DI roughly halves a big commercial report's time and cuts DI cost on every report.
4. Extract
Foundry · gpt-5.4-mini		 The report text plus the extraction instructions go to the Foundry-hosted gpt-5.4-mini deployment (the same instructions saved on the cibil-extractor agent), which returns the customer, every account and the enquiries as compact JSON. A small consumer report goes in one pass; a large commercial report is split per facility and its chunks run in parallel, then merged. Only an LLM turns messy, inconsistent report text into the exact schema reliably; per-facility chunking lets a 150+ page report be read completely without truncation; keyless via managed identity + RBAC.
5. Business rules
rules.py		 Normalises DPD, sequences accounts (peak-DPD first, then newest), builds ownership / loan-type / purpose summaries, derives NPA / SMA status, and runs 6 reconciliation checks against the printed totals. Math, sorting, totals and reconciliation must be exact and auditable — not left to the model — and cost zero extra tokens.
6. Maker review
Browser		 The extracted data, reconciliation and flags render for the maker to verify and edit. Human-in-the-loop for a regulated workflow.
7. Checker approval
Browser		 The checker confirms the reconciliation and approves — or rejects with a reason. Four-eyes control and a full audit trail.
8. Generate Excel
openpyxl		 On approval, the 5-sheet Full Detail workbook is filled (red DPD / overdue, totals row, DPD summary) to match the client template and streamed back to download. The output must match the exact template; openpyxl gives cell-level control including rich-text red.

Adaptive extraction — individual vs commercial reports

As soon as the text is read, the pipeline recognises which kind of CIBIL report it is and picks the matching extraction strategy — so a short consumer report and a 150+ page commercial report both come through cleanly.

Report typeHow it is recognisedExtraction strategy
Individual / Consumer CIR Compact account-summary table; no “Commercial Credit Information Report” header. The report is small, so its text goes to the model in a single pass.
Commercial CIR “Commercial Credit Information Report” header; each account is a repeated “Credit Facility N” block. Split on the per-facility boundary — a front-matter chunk (customer + credit summary + enquiries) plus batches of whole facility blocks — extracted in parallel and merged. Every facility is read exactly once, so account counts and totals reconstruct exactly even across 150+ pages.

Why it matters: a commercial report lists each tradeline as its own multi-page block, so a single model call would truncate a long report and repeat accounts. Splitting on the natural facility boundary keeps every account intact and lets long reports reconcile.

End-to-end sequence

Local PoC architecture

How the file is picked up

The browser file input hands the PDF to a multipart POST /api/extract. The bytes are parsed in memory with pypdfium2 straight from the byte stream — the file is never written to disk.

Where things are saved

Nothing is persisted to disk. The extracted JSON and the generated workbook live in an in-process job store keyed by a job id, for the session only. Downloads stream those bytes.

Does the faster PoC change this? The extraction step got quicker and keyless, but a multi-tenant, maker–checker, audit-logged workflow at 3.17 lakh reports/month still needs a queue (Service Bus), durable artifact storage (Blob), and a transactional store for state + audit + tenant isolation. That store stays relational (Azure SQL or PostgreSQL) and holds only workflow metadata — status, who/when, reject reasons, audit — not the PDFs or Excel. Compute is AKS + KEDA (with ACR + Workload Identity), replacing Container Apps.
